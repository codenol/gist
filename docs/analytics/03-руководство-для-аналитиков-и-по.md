# Руководство для аналитиков и ПО: Взаимодействие с ИИ и дизайнерами

> **Для кого:** Аналитики и ПО (Product Owners)  
> **Цель:** Понять, как правильно формулировать запросы дизайнерам и работать с ИИ, не нарушая границы ответственности

## Важно: Границы ответственности

### Кто отвечает за UX и UI?

**UX/UI дизайнер отвечает за:**
- ✅ Пользовательский опыт (UX) — как пользователь взаимодействует с интерфейсом
- ✅ Визуальный дизайн (UI) — как интерфейс выглядит
- ✅ Соответствие дизайн-системе
- ✅ Доступность (accessibility)
- ✅ Информационную архитектуру

**Аналитик и ПО отвечают за:**
- ✅ Бизнес-требования и метрики
- ✅ Пользовательские потребности и проблемы
- ✅ Данные и инсайты
- ✅ Технические ограничения (API, данные)
- ✅ Приоритизацию задач

**❌ Аналитик и ПО НЕ отвечают за:**
- ❌ Конкретные UI-решения (кнопки, модальные окна, расположение элементов)
- ❌ Визуальный дизайн (цвета, размеры, отступы)
- ❌ UX-паттерны (как пользователь взаимодействует с интерфейсом)
- ❌ Соответствие дизайн-системе

## Как правильно формулировать запросы дизайнерам

### ✅ Хороший запрос (фокус на проблеме и контексте):

**Цель:**
Пользователи не понимают, почему их заявка была отклонена. Нужно повысить прозрачность процесса рассмотрения заявок и снизить количество обращений в поддержку на 30%.

**Контекст:**
- Бизнес: снижение количества обращений в поддержку на 30%
- Пользователь: заемщики, которые подают заявку на кредит
- Технический: есть API для получения статусов заявки, данные обновляются раз в час
- Данные: есть история статусов, причины отклонения, временные метки

**Что НЕ нужно указывать:**
- ❌ Конкретные UI-элементы (кнопки, модальные окна, таблицы)
- ❌ Визуальные решения (цвета, размеры, расположение)
- ❌ Как должно выглядеть решение

**Почему это хорошо:**
Дизайнер получает полный контекст проблемы и может найти оптимальное решение с точки зрения UX/UI и дизайн-системы. Дизайнер несет ответственность за результат.

### ❌ Плохой запрос (конкретные UI-решения):

**Цель:**
Сделать страницу со статусом заявки с таймлайном и модальным окном с деталями.

**Контекст:**
- Нужна кнопка "Подробнее" справа вверху
- Таймлайн должен быть вертикальным
- Модальное окно должно открываться по клику

**Почему это плохо:**
1. Вы берете на себя ответственность за UX/UI решение, но не имеете экспертизы
2. Дизайнер не может найти оптимальное решение — вы уже задали конкретное
3. Если решение окажется плохим с точки зрения UX, ответственность размыта
4. ИИ видит конкретное решение и невольно начинает его реализовывать

## Что можно делать самостоятельно с ИИ

### ✅ Можно делать самостоятельно:

**1. Подготовка контекста для дизайнера:**
- Формулировать бизнес-цели и метрики
- Описывать пользовательские проблемы
- Собирать данные и инсайты
- Описывать технические ограничения

**Пример:**
```
**Цель:**
Пользователи тратят в среднем 3 минуты на поиск нужного отчета среди 50+ вариантов.

**Контекст:**
- Бизнес: нужно снизить время поиска до 30 секунд
- Пользователь: аналитики, которые используют отчеты ежедневно
- Технический: отчеты хранятся в иерархической структуре (категории → подкатегории → отчеты)
- Данные: есть данные о популярности отчетов, частоте использования, поисковых запросах
```

**2. Генерация технических требований:**
- Описание API и данных
- Технические ограничения
- Интеграции с существующими системами

**3. Подготовка документации:**
- Описание функциональности
- Пользовательские сценарии (user stories)
- Критерии приемки (acceptance criteria)

### ❌ НЕ нужно делать самостоятельно:

**1. Конкретные UI-решения:**
- ❌ "Нужна кнопка справа вверху"
- ❌ "Модальное окно должно открываться по клику"
- ❌ "Таблица должна быть с 5 колонками"

**2. Визуальные решения:**
- ❌ "Кнопка должна быть синей"
- ❌ "Текст должен быть размером 16px"
- ❌ "Отступы должны быть 24px"

**3. UX-паттерны:**
- ❌ "Информация должна быть в модальном окне"
- ❌ "Нужен таймлайн для отображения статусов"
- ❌ "Должна быть таблица с фильтрами"

**Почему:**
Эти решения требуют экспертизы дизайнера и влияют на пользовательский опыт. Если вы делаете их самостоятельно, вы берете на себя ответственность за UX/UI, но не имеете необходимой экспертизы.

## Работа с ИИ: Что можно и нельзя

### ✅ Можно использовать ИИ для:

**1. Подготовки запросов дизайнерам:**
```
Помоги мне сформулировать запрос дизайнеру:
- Проблема: пользователи не понимают, почему заявка отклонена
- Бизнес-цель: снизить обращения в поддержку на 30%
- Данные: есть история статусов, причины отклонения
```

**2. Структурирования контекста:**
```
Помоги структурировать контекст для дизайнера:
- Пользователь: аналитики
- Проблема: тратят 3 минуты на поиск отчета
- Данные: 50+ отчетов, есть данные о популярности
```

**3. Генерации технических требований:**
```
Создай технические требования для задачи:
- API для получения статусов заявки
- Данные обновляются раз в час
- Нужна история статусов
```

### ❌ НЕ используйте ИИ для:

**1. Генерации UI-решений:**
- ❌ "Создай дизайн страницы со статусом заявки"
- ❌ "Какой UI должен быть для отображения отчетов?"
- ❌ "Сделай модальное окно с деталями"

**Почему:**
ИИ не знает вашу дизайн-систему, контекст пользователей и лучшие практики UX. Решение будет поверхностным и может не соответствовать стандартам проекта.

**2. Принятия UX-решений:**
- ❌ "Должна ли информация быть в модальном окне?"
- ❌ "Как лучше отобразить статусы заявки?"
- ❌ "Какой паттерн использовать для поиска?"

**Почему:**
Эти решения требуют экспертизы дизайнера и понимания контекста пользователей. ИИ может предложить общее решение, но не учитывает специфику вашего продукта.

## Процесс работы: Рекомендуемый workflow

### Шаг 1: Подготовка запроса (Аналитик/ПО)

**Что делать:**
1. Сформулировать бизнес-цель и проблему пользователя
2. Собрать контекст (бизнес, пользователь, технический, данные)
3. Описать метрики успеха

**Что НЕ делать:**
- Предлагать конкретные UI-решения
- Описывать, как должно выглядеть решение

**Пример хорошего запроса:**
```
**Цель:**
Пользователи не понимают, почему их заявка была отклонена. Нужно повысить прозрачность процесса рассмотрения заявок.

**Контекст:**
- Бизнес: снижение количества обращений в поддержку на 30%
- Пользователь: заемщики, которые подают заявку на кредит
- Технический: есть API для получения статусов заявки, данные обновляются раз в час
- Данные: есть история статусов, причины отклонения, временные метки
```

### Шаг 2: Работа дизайнера

**Что делает дизайнер:**
1. Анализирует проблему и контекст
2. Изучает дизайн-систему и существующие паттерны
3. Создает UX/UI решение с использованием структурированного промпта для ИИ
4. Отвечает за качество решения с точки зрения UX/UI

**Результат:**
Дизайнер создает решение, которое соответствует:
- Бизнес-целям
- Пользовательским потребностям
- Дизайн-системе
- UX-паттернам

### Шаг 3: Согласование (Аналитик/ПО + Дизайнер)

**Что обсуждается:**
- Соответствие бизнес-целям
- Решение пользовательской проблемы
- Технические ограничения

**Что НЕ обсуждается (если дизайнер следует дизайн-системе):**
- Конкретные UI-элементы (если они из дизайн-системы)
- Визуальные решения (если они соответствуют дизайн-системе)

**Почему:**
Дизайнер — эксперт в UX/UI. Если решение соответствует дизайн-системе и решает проблему пользователя, не нужно вмешиваться в детали реализации.

## Чек-лист для аналитика/ПО

Перед отправкой запроса дизайнеру проверьте:

- [ ] Я описал проблему пользователя, а не решение
- [ ] Я указал бизнес-цели и метрики
- [ ] Я описал контекст (бизнес, пользователь, технический, данные)
- [ ] Я НЕ упомянул конкретные UI-элементы (кнопки, модальные окна, таблицы)
- [ ] Я НЕ описал визуальные решения (цвета, размеры, расположение)
- [ ] Я НЕ предложил конкретное UX-решение (как должно выглядеть)
- [ ] Я готов принять решение дизайнера, если оно соответствует бизнес-целям

## Частые ошибки и как их избежать

### Ошибка 1: Предлагать конкретные UI-решения

**❌ Плохо:**
```
Нужна страница со статусом заявки с таймлайном и кнопкой "Подробнее" справа вверху.
```

**✅ Хорошо:**
```
Пользователи не понимают, почему их заявка была отклонена. Нужно повысить прозрачность процесса рассмотрения заявок.
```

### Ошибка 2: Использовать ИИ для генерации UI

**❌ Плохо:**
```
ИИ, создай дизайн страницы со статусом заявки с таймлайном и модальным окном.
```

**✅ Хорошо:**
```
ИИ, помоги сформулировать запрос дизайнеру: проблема — пользователи не понимают причины отклонения заявки.
```

### Ошибка 3: Требовать конкретные визуальные решения

**❌ Плохо:**
```
Кнопка должна быть синей, размер 16px, отступы 24px.
```

**✅ Хорошо:**
```
Решение должно соответствовать дизайн-системе проекта.
```

## Резюме: Правила взаимодействия

1. **Вы отвечаете за:** бизнес-цели, пользовательские проблемы, данные, технические ограничения
2. **Дизайнер отвечает за:** UX/UI решения, соответствие дизайн-системе, пользовательский опыт
3. **Используйте ИИ для:** подготовки контекста, структурирования запросов, технических требований
4. **НЕ используйте ИИ для:** генерации UI-решений, принятия UX-решений
5. **Формулируйте запросы:** через проблему и контекст, без конкретных UI-решений
